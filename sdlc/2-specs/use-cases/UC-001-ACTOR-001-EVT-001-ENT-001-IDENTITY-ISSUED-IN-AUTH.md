# UC-001-ACTOR-001-EVT-001-ENT-001-IDENTITY-ISSUED-IN-AUTH

## Цель

Выдать постоянному или гостевому пользователю проверяемую идентичность для
доступа к защищённым операциям.

## Трассировка

- [PT-001](../../1-business-tasks/planning/PT-001.md)
- [PT-008](../../1-business-tasks/planning/PT-008.md)
- [ACTOR-001](../actors/ACTOR-001-USER-IN-QUEUE.md)
- [EVT-001](../events/EVT-001-IDENTITY-ISSUED-IN-AUTH.md)
- [ENT-001](../entities/ENT-001-USER-IN-AUTH.md)

## Предусловия

Для регистрации предоставлены валидные обязательные данные; для входа
существует постоянный профиль; для гостевого режима предварительный профиль не
требуется.

## Вход

- режим: `REGISTER`, `LOGIN` или `GUEST`;
- регистрационные данные либо credentials;
- correlation id.

## Основной поток

1. Сервис валидирует режим и данные.
2. Для `REGISTER` создаёт постоянный User; для `LOGIN` проверяет credentials;
   для `GUEST` создаёт временный User.
3. Роли загружаются из доверенного хранилища.
4. Сервис формирует подписанный JWT с `sub = user_id`.
5. Для гостя `exp = issued_at + 24h`.
6. Клиент получает access token и безопасный профиль.
7. Фиксируется EVT-001 без значения токена.

## Альтернативы и ошибки

- конфликт регистрации — профиль не создаётся повторно;
- неверные credentials — JWT не выдаётся;
- некорректные поля — ошибка валидации;
- клиентская попытка назначить роль игнорируется или отклоняется.

## Результат

Пользователь имеет JWT, по которому сервис однозначно восстанавливает User и
роли. Истёкший JWT не авторизует новую операцию.

## Критерии приёмки

1. Постоянная регистрация и вход выдают JWT.
2. Гость получает временного User и JWT ровно на 24 часа.
3. JWT/credentials отсутствуют в журналах.
4. `user_id` защищённых операций берётся только из JWT.
