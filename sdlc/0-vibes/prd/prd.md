# PRD: Queue Assignment

## 1. Сведения о документе

- **Продукт:** `queue_assignment`
- **Тип:** MCP-сервис электронной очереди
- **Статус:** Approved for decomposition
- **Версия:** 0.6
- **Дата:** 2026-08-03
- **Исходный материал:** [`../raw.txt`](../raw.txt)
- **Следующий этап:** `sdlc/1-business-tasks/`

## 2. Краткое описание

`queue_assignment` — сервис управления электронной очередью, доступный через
REST API и MCP-инструменты. Пользователи работают с очередью самостоятельно
либо через AI-агента, операторы управляют обслуживанием, а администраторы
создают и открывают очереди.

REST API и MCP должны использовать один слой бизнес-логики. AI-агент не имеет
прямого доступа к базе данных и выполняет операции только от имени
авторизованного пользователя с соблюдением тех же правил доступа, что и
обычный клиент.

## 3. Проблема

Организациям требуется единый и предсказуемый механизм управления очередями,
который:

- исключает ручное ведение списка ожидающих;
- обеспечивает порядок обслуживания по принципу FIFO;
- позволяет пользователю видеть своё место и отменять запись;
- позволяет оператору последовательно обслуживать пользователей;
- поддерживает работу AI-агентов без предоставления им прямого доступа к
  данным;
- безопасно обрабатывает повторные и конкурентные запросы.

Без такого механизма возможны дублирующиеся записи, нарушение порядка,
повторное выполнение команд, несанкционированные операции и расхождение
состояния между REST- и MCP-клиентами.

## 4. Цель продукта

Разработать минимально жизнеспособный сервис электронной очереди, который
предоставляет безопасные и согласованные операции через REST API и MCP,
поддерживает полный базовый цикл обслуживания и разворачивается в Docker одной
командой.

## 5. Цели MVP

1. Обеспечить регистрацию пользователей и выдачу JWT access token, включая
   гостевой JWT сроком на 24 часа.
2. Обеспечить создание, открытие и закрытие очередей.
3. Позволить пользователю записаться в открытую очередь, узнать позицию и
   отменить собственную активную запись.
4. Позволить оператору вызвать следующего пользователя, начать и завершить
   обслуживание.
5. Предоставить основные пользовательские операции через REST API и MCP
   Streamable HTTP.
6. Применять одинаковые правила авторизации и бизнес-логики ко всем
   интерфейсам.
7. Гарантировать атомарность и идемпотентность изменяющих операций.
8. Сохранять журнал вызовов MCP-инструментов.
9. Обеспечить локальный запуск всех компонентов через Docker Compose.
10. Предоставить публичное read-only табло всех очередей и активных участников.

## 6. Не входит в MVP

- интерактивный графический интерфейс пользователя или оператора, кроме
  публичного read-only табло очередей;
- бронирование конкретного времени;
- приоритетные, платные или многоуровневые очереди;
- перенос записи между очередями;
- уведомления по SMS, email или push;
- аналитическая панель и отчётность;
- мультитенантность;
- интеграция с внешней системой идентификации;
- автоматический выбор AI-провайдера или полноценный AI-ассистент;
- горизонтальное масштабирование и географическое резервирование;
- управление физическими терминалами и табло.

## 7. Пользователи и роли

### 7.1 Пользователь

Хочет занять место в очереди и понимать, когда будет обслужен.

Разрешённые действия:

- получить список доступных очередей;
- записаться в открытую очередь;
- получить текущую позицию собственной записи;
- отменить собственную активную запись.

Пользователь может быть постоянным или временным гостевым. Гость создаётся
сервисом без предварительной регистрации и получает JWT сроком на 24 часа.
После истечения токена гостевой доступ прекращается.

### 7.2 Оператор

Обслуживает пользователей в одной или нескольких очередях, назначенных
администратором.

Разрешённые действия:

- получить список доступных очередей;
- вызвать следующего пользователя;
- начать обслуживание вызванного пользователя;
- завершить текущее обслуживание.

Один оператор может одновременно обслуживать не более одной записи. Несколько
операторов одной очереди могут параллельно обслуживать разных пользователей.
Оператору разрешено видеть только номер талона, статус, время записи и
отображаемое имя пользователя.

### 7.3 Администратор

Управляет жизненным циклом очередей.

Разрешённые действия:

- создать очередь;
- открыть очередь;
- закрыть очередь;
- просматривать состояние очередей.
- назначать операторов на одну или несколько очередей.

### 7.4 AI-агент

Вызывает MCP-инструменты от имени авторизованного пользователя.

Ограничения:

- не имеет прямого доступа к базе данных;
- не получает дополнительных прав;
- не может подменить пользователя;
- не может обходить авторизацию, валидацию или бизнес-правила;
- все его вызовы MCP журналируются.

### 7.5 Публичный наблюдатель

Неавторизованный посетитель, который просматривает текущее состояние очередей
на публичном табло и не выполняет бизнес-операции.

Разрешено видеть:

- название и статус каждой очереди;
- число активных записей;
- для активной записи — номер талона, статус, время записи и отображаемое имя.

Email, внутренний идентификатор пользователя, роли, токены и завершённая
история на публичном табло не раскрываются.

## 8. Основные пользовательские сценарии

### US-00. Получение доступа

Как новый пользователь, я хочу зарегистрироваться и получить JWT access token.
Как гость, я хочу получить временный профиль и гостевой JWT сроком на 24 часа,
чтобы воспользоваться очередью без постоянной регистрации.

### US-01. Просмотр очередей

Как пользователь, я хочу получить список очередей и их состояние, чтобы
выбрать доступную очередь.

### US-02. Запись в очередь

Как пользователь, я хочу записаться в открытую очередь, чтобы получить
уникальный талон и место ожидания.

### US-03. Просмотр позиции

Как пользователь, я хочу узнать актуальную позицию своей записи, чтобы
оценивать время ожидания.

### US-04. Отмена записи

Как пользователь, я хочу отменить свою активную запись, если обслуживание мне
больше не требуется.

### US-05. Вызов следующего пользователя

Как оператор, я хочу вызвать первую ожидающую запись, чтобы соблюдать порядок
FIFO.

### US-06. Начало обслуживания

Как оператор, я хочу перевести вызванную запись в обслуживание, чтобы
зафиксировать начало работы.

### US-07. Завершение обслуживания

Как оператор, я хочу завершить обслуживаемую запись, чтобы освободить очередь
для следующего пользователя.

### US-08. Управление очередью

Как администратор, я хочу создавать, открывать и закрывать очереди, чтобы
контролировать доступность записи, а также назначать операторов на одну или
несколько очередей для организации обслуживания.

### US-09. Работа через AI-агента

Как авторизованный пользователь, я хочу выполнять доступные мне операции через
AI-агента с теми же гарантиями безопасности, что и через REST API.

### US-10. Публичное табло очередей

Как публичный наблюдатель, я хочу без авторизации видеть все очереди и активных
участников с их текущими статусами, чтобы понимать фактическую загрузку и ход
обслуживания.

## 9. Функциональные требования

### FR-00. Регистрация и аутентификация

Сервис должен:

- регистрировать постоянного пользователя;
- выдавать JWT access token после успешной аутентификации;
- создавать временного гостевого пользователя без предварительной регистрации;
- выдавать гостевому пользователю JWT со сроком действия 24 часа;
- определять пользователя и его роли только по проверенному JWT;
- отклонять истёкшие, некорректные и отозванные токены.

Точный срок действия постоянного access token, механизм обновления и правила
отзыва должны быть определены в спецификации аутентификации.

### FR-01. Управление очередями

Система должна позволять администратору:

- создать очередь;
- открыть закрытую очередь;
- закрыть открытую очередь;
- получить сведения о текущем состоянии очереди;
- назначить оператора на одну или несколько очередей;
- снять назначение оператора с очереди.

Новые записи допускаются только в очередь со статусом `OPEN`.

### FR-02. Запись пользователя

Система должна:

- определять пользователя по токену авторизации;
- создавать запись только в открытой очереди;
- запрещать пользователю более одной активной записи в одной очереди;
- назначать уникальный номер талона в пределах очереди;
- возвращать созданную запись и её текущую позицию.

Активными считаются состояния `WAITING`, `CALLED` и `SERVING`.
Пользователь может одновременно иметь по одной активной записи в нескольких
разных очередях.

Номер талона увеличивается последовательно в пределах очереди и в MVP не
сбрасывается при закрытии или повторном открытии очереди.

### FR-03. Получение позиции

Система должна возвращать позицию авторизованного пользователя среди записей
со статусом `WAITING`.

Позиция определяется порядком FIFO. Для записей в других состояниях система
должна возвращать состояние записи без позиции ожидания.

### FR-04. Отмена записи

Пользователь может отменить только собственную запись в состоянии `WAITING`
или `CALLED`. После успешной отмены запись переходит в `CANCELLED`.

### FR-05. Вызов следующего пользователя

Оператор может вызвать первую запись в состоянии `WAITING` в доступной ему
очереди. Выбранная запись переходит в `CALLED`.

Выбор записи и изменение её состояния должны выполняться атомарно, чтобы два
конкурентных запроса не вызвали одного пользователя дважды.

### FR-06. Начало обслуживания

Оператор может перевести доступную ему запись из `CALLED` в `SERVING`, если
этот оператор ещё не обслуживает другую запись. В одной очереди может
одновременно обслуживаться несколько записей разными назначенными операторами.

### FR-07. Завершение обслуживания

Оператор может перевести доступную ему запись из `SERVING` в `COMPLETED`.

### FR-08. Закрытие очереди

Закрытие очереди должно запрещать создание новых записей. Активные записи
сохраняются и могут быть обслужены после закрытия очереди.

### FR-09. REST API

REST API должно предоставлять операции MVP и:

- принимать и проверять токен авторизации;
- проверять роль и доступ к ресурсу;
- валидировать входные данные;
- возвращать единообразные успешные ответы и ошибки;
- принимать `Idempotency-Key` для всех изменяющих запросов.

### FR-10. MCP

Сервис должен предоставлять через транспорт MCP Streamable HTTP следующие
инструменты:

- `list_queues`;
- `join_queue`;
- `get_current_position`;
- `cancel_queue_entry`;
- `call_next_user`;
- `start_service`;
- `complete_service`.

Изменяющие инструменты должны принимать `idempotencyKey`.

Административные операции, включая создание, открытие и закрытие очередей и
назначение операторов, в MVP доступны только через REST API. Административные
MCP-инструменты в MVP отсутствуют.

Основной MCP endpoint `/api/mcp` использует Streamable HTTP. Для клиентов
старого транспорта доступен legacy HTTP+SSE endpoint: `GET /api/sse` открывает
поток и сообщает отдельный `POST /api/sse/messages` для JSON-RPC сообщений.
`POST /api/sse` также принимается как совместимый Streamable HTTP alias.
Помимо JWT в Bearer-заголовке MCP принимает отзываемый долгоживущий access
token в query-параметре `token`.

### FR-11. Общая бизнес-логика

REST-контроллеры и MCP-инструменты должны обращаться к одним и тем же
прикладным операциям. Дублирование правил между интерфейсами не допускается.

### FR-12. Идемпотентность

Для изменяющей операции повторный запрос с тем же ключом, пользователем,
операцией и эквивалентными параметрами должен возвращать исходный результат и
не создавать повторный эффект.

Повторное использование ключа с отличающимися параметрами должно завершаться
ошибкой конфликта.

Результаты идемпотентности хранятся 24 часа.

### FR-13. Журнал MCP

Каждый вызов MCP-инструмента должен сохраняться в `McpToolCall`, включая:

- идентификатор вызова;
- имя инструмента;
- идентификатор пользователя;
- идентификатор AI-агента, если доступен;
- безопасное представление входных параметров;
- результат выполнения или категорию ошибки;
- время начала и завершения;
- `idempotencyKey`, если применимо.

Секреты и токены авторизации не должны записываться в журнал.
MCP-журнал хранится 30 дней.

### FR-14. Публичное табло очередей

Сервис должен предоставлять открытую Blade-страницу `GET /queues-board`, не
требующую JWT. Страница должна:

- отображать все очереди, включая `OPEN` и `CLOSED`;
- для каждой очереди отображать только активные записи в состояниях
  `WAITING`, `CALLED`, `SERVING`;
- показывать число активных записей;
- показывать для записи только номер талона, статус, время постановки,
  отображаемое имя и доступные временные отметки вызова/обслуживания;
- не показывать email, пароль, JWT/MCP-токен, роли или внутренний `user_id`;
- сохранять FIFO-порядок отображения по `joined_at`, затем `id`;
- корректно показывать пустое состояние очереди;
- автоматически обновляться не реже одного раза в 30 секунд;
- не предоставлять изменяющих действий.

## 10. Доменная модель

### 10.1 Queue

Минимальные поля:

- `id`;
- `name`;
- `status`;
- `created_at`;
- `updated_at`.

Состояния:

- `OPEN`;
- `CLOSED`.

### 10.2 QueueEntry

Минимальные поля:

- `id`;
- `queue_id`;
- `user_id`;
- `ticket_number`;
- `status`;
- `joined_at`;
- `called_at`;
- `service_started_at`;
- `completed_at`;
- `cancelled_at`;
- `created_at`;
- `updated_at`.

Состояния:

- `WAITING`;
- `CALLED`;
- `SERVING`;
- `COMPLETED`;
- `CANCELLED`.

Допустимые переходы:

```text
WAITING → CALLED → SERVING → COMPLETED
   │         │
   └─────────┴────→ CANCELLED
```

Другие переходы должны отклоняться.

### 10.3 McpToolCall

Минимальные поля:

- `id`;
- `tool_name`;
- `user_id`;
- `ai_agent_id`;
- `idempotency_key`;
- `request_payload`;
- `response_payload`;
- `status`;
- `error_code`;
- `started_at`;
- `finished_at`.

### 10.4 Связанные сущности

- `User` — постоянный или временный гостевой пользователь, зарегистрированный
  сервисом и имеющий одну или несколько ролей.
- `AiAgent` — идентифицированный MCP-клиент, выполняющий действия от имени
  пользователя.
- назначение оператора связывает пользователя с ролью оператора и одной или
  несколькими очередями.

Формат ролей, поля регистрации, правила постоянных JWT и способ регистрации
AI-агентов уточняются в спецификации.

## 11. Бизнес-правила

1. Ожидающие обслуживаются в порядке FIFO по моменту успешной записи.
2. При одинаковом времени порядок определяется стабильным уникальным
   идентификатором записи.
3. Пользователь может иметь не более одной активной записи в одной очереди.
   Одновременные активные записи в разных очередях разрешены.
4. Номер талона уникален, монотонно увеличивается в пределах очереди и в MVP
   не сбрасывается.
5. Запись возможна только в очередь `OPEN`.
6. Пользователь может просматривать и изменять только собственные записи.
7. Пользователь может отменить запись в состоянии `WAITING` или `CALLED`.
8. Оператор может выполнять операции только в назначенных ему очередях.
9. Один оператор может иметь не более одной записи в `SERVING`; разные
   операторы могут параллельно обслуживать записи одной очереди.
10. Оператор видит только талон, статус, время записи и отображаемое имя.
11. Управление очередями и назначениями операторов доступно администратору
    только через REST API.
12. AI-агент наследует полномочия пользователя, а не расширяет их.
13. Все изменения состояния должны выполняться в транзакции.
14. Недопустимые переходы состояния должны отклоняться без частичного эффекта.
15. Повторный идемпотентный запрос не должен повторять бизнес-операцию.
16. Публичное табло раскрывает только активные записи и минимальный
    согласованный набор отображаемых данных; завершённые и отменённые записи
    на нём отсутствуют.

## 12. Авторизация и безопасность

- Все бизнес-операции, кроме регистрации, аутентификации и создания гостевой
  сессии, требуют авторизации. Технические проверки состояния сервиса и
  read-only табло очередей доступны без JWT.
- Сервис регистрирует пользователей и выдаёт JWT access token.
- Для гостевого режима сервис создаёт временного пользователя и выдаёт
  гостевой JWT сроком на 24 часа.
- Пользователь определяется по проверенному JWT либо по хешированному,
  отзываемому MCP access token, а не по идентификатору во входных параметрах.
- Для каждой операции выполняется проверка роли, принадлежности ресурса и
  области доступа.
- MCP-сервер не предоставляет произвольный доступ к базе данных.
- Входные данные валидируются до выполнения бизнес-операции.
- Ошибки не должны раскрывать токены, секреты, SQL или внутренние трассировки.
- Публичный доступ осуществляется по HTTPS с терминацией TLS на Nginx.
- Секреты передаются через переменные окружения или механизм секретов и не
  хранятся в репозитории.
- Для чувствительных операций должна сохраняться аудит-информация.
- Публичное табло использует белый список полей и не возвращает email,
  внутренний `user_id`, роли, секреты или терминальную историю.

## 13. Нефункциональные требования

### NFR-01. Целостность

Операции записи и смены состояния должны быть атомарными. Ограничения
уникальности должны обеспечиваться не только приложением, но и базой данных,
где это возможно.

### NFR-02. Конкурентность

Система должна корректно обрабатывать одновременную запись пользователей и
одновременные запросы операторов на вызов следующего пользователя.

### NFR-03. Производительность

Для MVP при штатной нагрузке 95-й перцентиль времени ответа без учёта внешнего
AI-провайдера должен быть не более 500 мс.

Целевой объём MVP:

- до 100 очередей;
- до 1000 активных записей в одной очереди;
- до 20 входящих запросов в секунду.

Соответствие этим значениям должно быть подтверждено нагрузочным тестированием.

### NFR-04. Наблюдаемость

Приложение должно предоставлять:

- структурированные журналы;
- идентификатор корреляции запроса;
- health-check для приложения и зависимостей;
- диагностируемые категории ошибок;
- журнал MCP-вызовов.

### NFR-05. Хранение данных

- записи очередей хранятся 90 дней;
- результаты идемпотентности хранятся 24 часа;
- журнал MCP-вызовов хранится 30 дней;
- удаление или архивирование по окончании срока не должно нарушать целостность
  активных операций.

### NFR-06. Тестируемость

Проверка MVP должна быть многоуровневой и воспроизводимой:

- unit-тесты изолированно проверяют JWT и чистую доменную/прикладную логику;
- feature-тесты проверяют REST, MCP, Blade, console-команды, middleware,
  авторизацию, валидацию и работу с БД;
- acceptance-тесты трассируются к каждому UC-001–UC-016 и явно различают
  `PASS`, `FAIL`, `INCOMPLETE` и `SKIPPED`;
- contract/parity-тесты подтверждают схемы REST/MCP и одинаковые правила общей
  операции;
- integration-тесты выполняются с MariaDB, Redis, Nginx и обоими MCP transport;
- конкурентные тесты проверяют уникальность активной записи и талона, FIFO,
  `call-next`, `cancel` против `call`, ограничение `SERVING` и идемпотентность;
- нагрузочный профиль подтверждает 20 RPS, p95 ≤ 500 мс, 100 очередей и до
  1000 активных записей в очереди;
- deployment smoke-тест проверяет чистый запуск, миграции, seeder, health,
  HTTPS, REST, MCP и публичное табло;
- security/privacy-проверки подтверждают матрицу ролей, владение, отсутствие
  секретов в ответах/логах и белый список публичных полей;
- UI-проверки табло включают desktop/mobile, empty state, FIFO, auto-refresh,
  отсутствие изменяющих controls и базовую доступность.

Тесты не должны обращаться к production-базе. Быстрые unit/feature/acceptance
наборы используют изолированную тестовую БД; проверки поведения конкретного
движка выполняются в отдельном одноразовом интеграционном Docker-контуре.
Каждый прогон сохраняет датированный отчёт и машинный CI-артефакт с release или
commit id, командами, окружением, результатами и известными пробелами.

### NFR-07. Развёртывание

Проект должен запускаться командой:

```bash
docker compose up -d
```

Минимальный состав контейнеров:

- `app`;
- `nginx`;
- `db`;
- `redis`.

После запуска должны быть доступны выполнение миграций, запуск тестов и работа
MCP Streamable HTTP и legacy HTTP+SSE через публичный HTTPS-адрес. TLS
завершается на Nginx.

Публичное табло должно формироваться одним чтением с eager loading без
N+1-запросов и корректно отображаться на настольных и мобильных экранах.

- Redis;
- MCP Server;
- OpenAI API или совместимый AI-провайдер;
- Docker;

Redis предполагается использовать для инфраструктурных задач, включая

## 15. Ошибки предметной области

Интерфейсы должны единообразно различать как минимум следующие случаи:

- пользователь не авторизован;
- действие запрещено;
- очередь не найдена;
- очередь закрыта;
- активная запись уже существует;
- запись не найдена;
- запись принадлежит другому пользователю;
- недопустимый переход состояния;
- в очереди нет ожидающих пользователей;
- конфликт ключа идемпотентности;
- некорректные входные данные;
- временная внутренняя ошибка.

Конкретные HTTP-статусы, MCP error codes и схемы ответов определяются в
спецификации API.

## 16. Критерии приёмки MVP

MVP считается функционально готовым, если:

1. Администратор может создать, открыть и закрыть очередь через REST API.
2. Сервис регистрирует пользователя и выдаёт JWT; гостевой режим создаёт
   временного пользователя с JWT сроком на 24 часа.
3. Администратор назначает оператора на одну или несколько очередей.
4. Авторизованный пользователь может записаться в открытую очередь и получает
   уникальный талон.
5. Повторная активная запись того же пользователя в ту же очередь исключена,
   а активные записи в разных очередях разрешены.
6. Пользователь может получить актуальную позицию и отменить свою запись в
   состоянии `WAITING` или `CALLED`.
7. Пользователь не может читать или изменять чужую запись.
8. Оператор последовательно переводит запись по цепочке
   `WAITING → CALLED → SERVING → COMPLETED`.
9. Один оператор обслуживает не более одной записи, но разные операторы могут
   параллельно обслуживать пользователей одной очереди.
10. Оператору доступны только талон, статус, время записи и отображаемое имя.
11. `call_next_user` выбирает первую ожидающую запись по FIFO.
12. Конкурентные вызовы не обслуживают одну запись повторно.
13. Повтор изменяющего запроса с тем же ключом не создаёт дополнительного
   эффекта.
14. REST API и MCP демонстрируют одинаковое поведение для общей операции.
15. MCP работает через Streamable HTTP и совместимый legacy HTTP+SSE и не
    содержит административных инструментов.
16. Все MCP-вызовы журналируются без сохранения секретов.
17. Проверки ролей применяются ко всем защищённым операциям.
18. Unit, feature и acceptance tests подтверждают UC-001–UC-016, позитивные и
    негативные сценарии, ошибки, роли и переходы состояний; непокрытый или ещё
    не реализованный сценарий явно отмечен и не считается пройденным.
19. Сервис выдерживает целевой объём до 100 очередей, 1000 активных записей в
    очереди и 20 запросов в секунду.
20. Данные удаляются или архивируются согласно согласованным срокам хранения.
21. Сервис запускается через Docker Compose, завершает TLS на Nginx и проходит
    health-check.
22. Инструкция запуска позволяет развернуть проект в чистом окружении.
23. Без JWT доступно публичное Blade-табло всех очередей; оно показывает только
    активные записи, согласованные публичные поля и автоматически обновляется.
24. Integration, contract/parity, concurrency, load, deployment smoke,
    security/privacy и UI-проверки выполнены в подходящем окружении, а их
    результаты сохранены как трассируемые артефакты конкретного release.

## 17. Метрики успеха

Для пилотного использования предлагаются следующие метрики:

- доля успешно завершённых валидных операций — не менее 99%;
- отсутствие дублирующих активных записей при конкурентных запросах;
- отсутствие повторных эффектов для корректно повторённых идемпотентных
  запросов;
- отсутствие нарушений FIFO в принятых сценариях;
- 100% MCP-вызовов имеют запись в журнале;
- 100% критических операций защищены проверкой авторизации;
- развёртывание в чистом окружении выполняется одной командой после настройки
  переменных окружения.

Точные SLO для промышленной эксплуатации находятся вне MVP.

## 18. Риски и способы снижения

| Риск | Последствие | Снижение |
|---|---|---|
| Гонки при вызове следующего пользователя | Повторный вызов одной записи | Транзакции, блокировка строк, конкурентные тесты |
| Неполная идемпотентность | Дублирование записей и переходов | Уникальные ключи, хранение результата, проверка параметров |
| Расхождение REST и MCP | Разное поведение клиентов | Общий прикладной слой и контрактные тесты |
| Подмена пользователя AI-агентом | Несанкционированный доступ | Проверенный контекст авторизации, запрет `user_id` из пользовательского ввода |
| Утечка данных в MCP-журнал | Компрометация секретов | Маскирование и белый список журналируемых полей |
| Ошибка назначения оператора | Доступ к чужим очередям | Назначение администратором и проверка связи с очередью |
| Неоднозначность закрытия очереди | Потеря активных записей | Зафиксированное правило: закрытие запрещает только новые записи |

## 19. Зависимости

- доступная MariaDB/MySQL;
- доступный Redis;
- Nginx с HTTPS-терминацией;
- MCP-клиент или AI-агент для интеграционного тестирования;
- CI-среда для автоматических тестов.

## 20. Принятые продуктовые решения

| ID | Вопрос | Решение |
|---|---|---|

| DEC-002 | Участие в очередях | Разрешена одна активная запись в каждой очереди и одновременное участие в разных очередях |
| DEC-003 | Назначение операторов | Администратор назначает оператора на одну или несколько очередей |
| DEC-004 | Параллельное обслуживание | Один оператор обслуживает не более одной записи; разные операторы могут параллельно обслуживать записи одной очереди |
| DEC-005 | Отмена после вызова | Отмена разрешена в `WAITING` и `CALLED` |
| DEC-006 | Нумерация талонов | Последовательно увеличивается в пределах очереди и не сбрасывается в MVP |
| DEC-007 | Данные для оператора | Талон, статус, время записи и отображаемое имя |
| DEC-008 | MCP-транспорт | Streamable HTTP |
| DEC-009 | HTTPS | TLS завершается на Nginx |
| DEC-010 | Целевой объём | До 100 очередей, 1000 активных записей в очереди и 20 запросов в секунду |

| DEC-013 | URL-подключение MCP | `/api/sse?token=...` поддерживает legacy HTTP+SSE с отдельным `/api/sse/messages`; `POST /api/sse` сохранён как Streamable HTTP alias; токен отзываемый, хранится только как SHA-256-хеш, query string исключается из access log Nginx |

## 21. Условия передачи на следующий этап

- назначены владельцы продукта и технического решения;
- приняты и отражены в требованиях все блокирующие продуктовые решения;
- определены приоритеты пользовательских сценариев;
- зафиксированы измеримые критерии успеха;
- бизнес-задачи сохраняют ссылку на этот документ как на исходный артефакт.
